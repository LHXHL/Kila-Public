摘要：

Codex 、 Claude Code 这类成熟 Agent 已经让很多人习惯了“把复杂任务交给 AI”。而当 Agent 真正进入日常工作，新的问题就变成：项目、模型、工具、消息入口和重复任务，怎样才能不散落在不同地方？ Kila 想做的是一个本地优先的开源 Agent 工作台，把这些东西组织进同一套可长期维护的工作流。

先说结论

Kila 不想替代你已经习惯的成熟 Agent 。它想提供的是一种更容易按自己的项目、工具、消息入口和工作节奏来组织 Agent 的方式。

很多人第一次用成熟 Agent 时，都会有一个很兴奋的时刻。

它能读项目、改文件、跑命令、处理复杂任务。你会觉得：终于不是一个只会聊天的 AI 了。

但当 Agent 不再只是偶尔打开的终端工具，而是真的进入每天的项目和事务，难点会变成另一件事：怎么把零散能力组织成一套不断线的工作流。

安全审计有自己的项目、范围和报告口径；研发项目有自己的文件、工具和权限；内容创作有自己的表达习惯。再加上飞书、微信、 Telegram 、 Discord 这些消息入口，以及每天、每周都要推进的重复事项——它们不该散落在一堆对话、脚本和临时提醒里。

Kila 的做法很直接：把项目、模型、 MCP 、 Skills 、规则、消息入口和定时任务，放进一个可持续使用的本地工作台。

比如，你可以提前把“飞书安全群”绑定到一个特定的安全审计 Session ，把“微信私聊”绑定到个人助理 Session ；也可以给一个项目配好模型、权限、 MCP 、 Skills ，再让定时任务把结果送回原来的对话或指定 IM 入口。

继续处理上周那个上传问题，按之前的审计口径来。
已进入你预先绑定的“上传审计” Session 。我会沿用这里已有的范围、证据和报告规则；不确定的部分单列为待验证项。

这里没有什么“比 Codex 更懂你”的魔法。 Kila 的价值是把这些关系——项目、规则、模型、工具、消息入口和自动化——做成一个可以看见、配置和长期维护的本地工作台，而不是让你每次靠临时上下文、脚本和不同入口重新拼起来。

"Kila 不发明另一种更聪明的 Agent ；它尝试把你已经认可的 Agent 能力，组织成一套更容易长期使用的个人工作环境。"
01 · Kila 和 Codex / Claude Code ，不是能力高低之争

它们能做很多相同的事，差别在你想怎样把它们用进日常

先说清楚： Kila 不是要替代 Codex 、 Claude Code 这类成熟 Agent 。

如果你已经在终端里把 Codex 或 Claude Code 用得很顺，它们当然可以继续是解决复杂工程问题的主力。

Kila 的定位更朴素：它不是为了证明“谁更强”，而是提供另一种把能力组织进日常工作流的产品形态。

它把这些通常需要分散维护的东西，收在一个本地优先的桌面应用里：

•一个 Session 绑定一个项目目录，围绕同一个工作现场持续推进；
•不同项目分别配置 MCP 、 Skills 、权限和模型偏好；
•将飞书、微信、 Telegram 、 Discord 等消息入口，显式绑定到指定 Session 或项目；
•创建带项目上下文的定时任务，并把结果送回 Session 或消息入口；
•用可查看、可编辑、可删除的本地文件保存配置、会话和记忆。

Kila 想降低的，是把这些能力组织成一套自己用得懂、找得到、改得动的工作流的成本。

换句话说， Codex 或 Claude Code 可以是非常强的 Agent ； Kila 则提供一个让你按本地项目、多个模型、多个消息入口来管理 Agent 工作的开源桌面工作台。两者可以重叠，也可以配合，关键不在于谁替代谁。

如果你喜欢 Codex 或 Claude Code ，没必要换掉它们。 Kila 想服务的，是“我想把 Agent 按自己的方式长期用起来”这件事。

02 · 先把 AI 调成“像你”的样子

自定义的重点，不是换语气，而是建立做事方式

很多产品也讲“个性化”。

但大多数时候，个性化只是换一种语气：更活泼、更专业、更像某个角色。

这当然有趣，但真正好用的个性化，应该是让 Agent 知道：你在乎什么、讨厌什么、什么情况下先停下来问你。

在 Kila 里，你可以给 Agent 写下长期有效的工作规则。它不只是一次性 Prompt ，而是你自己的协作说明书。

如果你是开发者：

工作规则
给代码助手的规则 默认用中文。先给结论，再给分析。修改代码前先说准备动哪些文件；不要为了一个小问题顺手重构半个项目；改完必须告诉我怎么验证；不确定的地方直接说不确定。

如果你是做安全研究的：

安全边界
给安全助手的规则 只处理已授权目标。先列证据，再下结论；把“已确认”和“待验证”分开；每个发现都要有触发条件、影响、验证思路和修复建议；高风险动作先问我。

如果你写内容：

表达偏好
给写作助手的规则 不要套话，不要硬凹金句；先用一个真实场景把读者拉进来；少说“赋能”“颠覆”；观点可以直接，但不要假装无所不知；结尾不要强行煽情。

更重要的是， Kila 不要求你只有一个“万能助手”。同一个人可以在不同项目里，拥有不同的 Agent 工作方式。

1
开源项目：它是谨慎的维护者，优先小改动、可验证、不乱动架构。
2
安全审计：它是证据优先的研究搭档，先范围、再证据、最后结论。
3
内容创作：它是知道你不喜欢“官方腔”的编辑，帮你保住自己的表达。
4
个人事务：它是轻量助理，记录、整理、提醒，把零散事情接住。

不是每个任务都该用同一种 AI 。 Kila 想给你的，是把 AI 调成适合当前工作的能力。

03 · 安全攻防场景里，最怕的不是不会做，而是上下文和边界丢了

它可以是一个守规则的安全研究搭档

安全研究是特别适合 Agent 协作、也特别需要边界感的场景。

一次授权测试或代码审计，通常不是“发现一个问题”就结束了。你还要持续处理范围、资产、证据、假设、复现条件、风险判断、报告草稿和修复建议。

中间最怕两件事：

•研究上下文断掉，前面确认过的范围和证据又要重新讲；
•Agent 把“推测”“待验证”“已确认”混成一句结论。

Kila 可以把一次研究放进独立项目 Session ：文件、对话、工具调用、项目规则和过程都围绕同一个工作现场展开。




授权范围 → 先明确目标、限制与不可触碰的边界



代码与证据 → 围绕文件、调用链、日志和现象逐步梳理



验证过程 → 区分已确认问题、待验证假设与需要人工确认的动作



报告输出 → 按触发条件、影响、验证思路、修复建议沉淀为可交付结果

你可以这样交代任务：

这是一个授权测试项目。先别做外部扫描，也不要修改文件。先帮我梳理上传链路，按“现象、证据、待验证点、建议”输出。
我会按已授权范围分析；先整理现有证据，并把无法确认的部分单列为待验证项。

它不是替你越界执行攻击，而是让你在授权研究、代码审计、 CTF 和防御分析中，少丢上下文，少漏边界，更快把零散发现变成清楚的结论。

"对安全研究者来说，真正有价值的不是一个“什么都敢做”的 AI ，而是一个知道范围、重视证据、能把过程留住的搭档。"
04 · 记忆，只负责让你少解释一点

长期记忆不是主角，但该记住的别每次从头说

Kila 的记忆功能不该抢走你的工作流，它只解决一个很朴素的问题：下一次开始时，少让你解释一点。

例如，它可以帮助你沉淀长期有效的内容：项目约束、表达偏好、已经确认的事实、还没有完成的事项，以及你主动留下的笔记。

请记住：这个项目不引入数据库；所有外部请求都必须有超时和错误处理；报告默认先写结论，再列证据。
已记住。后续涉及这个项目时，我会按这些约束处理，并在必要时提醒你确认。

但“记住”必须由你掌控。 Kila 的记忆和本地笔记可以查看、整理和删除；你可以决定是否自动检索相关记忆，也可以让某一轮对话不写入记忆。

记忆不是为了让 AI 假装无所不知，而是把真正长期有用的几条信息留在该留的位置。

05 · 一个项目，就是一个不容易串线的工作现场

它不只记得你，也知道你正在做什么

Kila 的 Session 不只是聊天记录。

你可以把它理解成一个项目的工作现场：对话在这里、文件在这里、项目规则在这里、使用的工具和能力在这里，后续的工作也可以在这里继续。

这对多项目并行的人很重要。

你不用在“安全审计”“产品开发”“开源维护”“内容写作”之间手动背着一大段背景来回跑。不同项目可以各自保持自己的规则和上下文，减少串线，也减少每次重新交接。

你不是在保存一次聊天，而是在留下一个可继续推进的工作现场。

06 · MCP 和 Skills ：让它在合适的项目里，调用合适的能力

不只是“会得更多”，而是知道该用什么

如果说模型决定了 Agent 能思考到什么程度，那么 MCP 和 Skills 决定了它在具体工作中可以连接什么、调用什么、遵循什么流程。

你可以按项目接入需要的能力：读资料、处理文档、连接服务、调用工具，或者加载一套已经写好的工作方法。

重点不在于把能力堆得越多越好，而在于让能力跟着项目走。

•做安全研究，就加载对应的研究规范和工具；
•做内容，就加载选题、改稿、排版相关的能力；
•做开发，就接入项目需要的服务和协作工具；
•不相关的能力，不必默认塞进每一段对话里。

这样一来， Agent 不会只是“什么都懂一点”的聊天机器人，而是能在不同项目里呈现出不同工作能力的协作者。

07 · 不同任务，用不同模型；你的工作台不该只认一家

模型是选择，不是绑定

有人偏好某个云端模型的推理和代码能力；有人希望接入兼容接口；也有人在特定任务里更看重本地运行和可控性。

Kila 支持多种模型渠道和兼容接口。你可以按任务、成本、速度、隐私要求和个人习惯做选择，而不用因为换模型，就把整个工作方式换掉。




复杂代码任务 → 选择你信任的强模型



日常整理与轻量事务 → 选择更快、更经济的模型



对本地和私密性更敏感的任务 → 使用你自己可控的部署方式

真正应该稳定下来的，不是“永远只用一个模型”，而是你自己的项目、规则、工作流和数据归属。

08 · 飞书、微信、 Telegram 、 Discord 里的消息，也能回到正确的工作里

不是让 AI 到处聊天，而是让工作不断线

很多任务不是在电脑前开始、也不是在电脑前结束。

你可能在飞书群里看到一条问题；在微信上想起一个待办；出门后用 Telegram 发一句远程指令；或者在 Discord 的社区里收到需要跟进的信息。

Kila 的 IM Bridge 可以把这些消息入口，连接到对应的 Kila Session 。




飞书研发群 → 进入研发项目 Session



飞书安全群 → 进入安全审计 Session



微信个人消息 → 进入个人助理 Session



Telegram 远程指令 → 进入指定项目的维护 Session



Discord 社区讨论 → 进入对应的协作或资料整理 Session

这意味着，你在飞书里问“上周那个构建问题最后怎么处理的？”， Agent 可以回到对应项目的上下文里找答案；你在微信里补一句“以后周报先写结论”，它也能变成你的工作偏好。

前提仍然是：由你配置连接和允许的用户 / 渠道。消息连接的价值不是无边界地把 AI 塞进每个聊天框，而是让需要继续的工作，不因为换了入口就断掉。

09 · 把总会忘的事，交给理解上下文的 Agent

定时任务，不只是“到点提醒”

有一类事情没什么技术含量，却特别消耗人：重复、定时、容易忘。

比如每天整理项目进度、每周汇总变更和待办、定期跑一次检查，再把结果送回对应的 Session 。

你可以先用自然语言描述想做什么：

每天上午 9 点，总结当前项目的进度、阻塞项和今天最值得优先做的三件事。
我先为你生成一个可核对的任务草稿，确认后再创建和启动。

Kila 会先给出可核对的任务草稿，确认后再创建。任务运行后的结果也会回到相应 Session ，而不是变成一个找不到上下文的孤立通知。

把重复劳动交给一个已经理解项目的 Agent ，才比单纯的提醒更有意义。

10 · 你的工作资产，应该留在自己手里

本地优先，不是口号

AI 工具用久了，很多人都会开始在意：我的对话、项目背景、规则、笔记和配置，最后到底在哪里？

Kila 选择本地优先。会话、项目配置、记忆、附件和工作数据默认保存在本机，更像一个可以自己整理、备份、迁移的工作目录，而不是一个看不见、带不走的黑箱。

当然，本地优先不代表调用云端模型时数据不会经过网络。你选择什么模型、连接什么服务，仍然需要自己判断。

但至少，你长期积累下来的项目历史、个性化规则、记忆、工具和方法，不必天然被锁进一个不可见的地方。

最后：成熟 Agent 很强，但你也值得拥有一套自己的工作方式

我们不缺一个会回答问题的模型，也不缺越来越强的通用 Agent 。

真正稀缺的，是一套能按你的项目、你的规则、你的消息入口和你的生活节奏来工作的 Agent 环境。

它可以接入你信任的成熟模型；
可以在不同项目里扮演不同角色；
可以守住安全研究的边界；
可以记住少量真正重要的信息；
可以在飞书、微信、 Telegram 、 Discord 和桌面之间不断线；
也可以把重复的工作，变成可确认、可追踪的定时任务。

"Kila 不想替代你已经喜欢的 Agent 。它想做的，是让这些能力最终能服务于你自己的工作方式。"
